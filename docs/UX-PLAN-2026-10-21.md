## P1 · ÖZELLEŞTİRİLEBİLİR SAĞ PANEL (katlanır · split · modüller)

> **22.10.2026 — F1 uygulandı (UX-045):** ortak `RightPanel` + modüller
> (Kanıtlar / İşlem / Planlananlar / Bağlam); ekran asideleri portalle taşındı.
>
> **28.10.2026 — ✅ tamamlandı (T64/P1):** modül seçimi eklendi
> (`src/core/panel-prefs.ts`, `.rp-modules` menüsü, `residue.panel.hidden`);
> sıra ekran planından, son görünür modül gizlenemez (`f51ab41`).
> Katlanır + `localStorage` + 1180px altında gizli. **F3 açık:** sürüklenebilir
> split genişliği ve kullanıcı modül seçimi/sıralaması.

### Neden
Sağ sütun bugün sadece "kanıt detayları" harcamak için ayrılmış durumda ve
ekranın ~%20'sini kaplıyor. Kullanıcı:
1. **Katlayabilmek** istiyor — daraltıldığında yer geri gelsin.
2. **Boyutunu ayarlayabilmek** istiyor — "ortadan bir split atarak".
3. **İçeriğini özelleştirebilmek** istiyor — başka modüller de aynı yere gelsin.

### Tasarım
Sağ panel **modül** tabanlı olur. Motor modülleri üretir (id, başlık, satırlar),
kullanıcı hangilerini göreceğini seçer. Yeni modül eklemek = motora bir modül
eklemek; arayüzde değişiklik gerekmez.

**Modül kataloğu (ilk sürüm):**

| id | İçerik | Neden |
|---|---|---|
| `safety` | "NEDEN GÜVENLİ?" — plan → yazılı onay → kasa | Tezi hatırlatan tek metin |
| `scan` | Tarama durumu, son tarama, kapsam | UX-001 raporunun özeti |
| `disk` | Sürücü, toplam, boş, doluluk | UX-004'ün paydası |
| `verdicts` | Önerilen / sor / rapor / korunuyor sayıları | UX-010: ekranın altında kalan en açıklayıcı veri |
| `ledgers` | Korunan / geri kazanılabilir / kasa / araçlar | Ana defter |
| `plans` | Bekleyen plan, kayıtlı plan, zamanlanmış iş | P3'ün rozet sayıları |
| `server` | Arayüz, çalışma dizini, ev dizini, sürüm | Sunucu bağlamı |

### Şema (motor → sözleşme)

```ts

  id: PanelModuleId;
```

### Katlama + split davranışı
- Geniş ekran: sağ sütun `320px` (bugünkü) ile `640px` arasında **sürüklenebilir**.
  Tutamak `role="separator"` + `aria-orientation="vertical"` + `aria-valuenow`;
  ok tuşlarıyla 16px adım, `Home`/`End` ile sınırlar.
- **Katlanma:** tutamacın üstündeki düğme sütunu `0`'a çeker → sağ panel gizlenir,
  ana alan tam genişlik olur. Aynı düğme geri açar. Durum `localStorage`'da.
- Dar ekran (<1180px): sağ panel zaten gizli; panel bir **açılır katman** olarak
  sunulur (aynı `SplitPanel` bileşeni, sabit genişlik modunda).

### Kabul ölçütü
- [ ] Panel modülleri API'den gelir; arayüz hiçbir metin üretmez.
- [ ] Sütun sürüklenerek 320→640px arası değişir; klavye ile de değişir.
- [ ] Katlama düğmesi sütunu gizler, tekrar basınca geri getirir.
- [ ] Kullanıcı modülleri seçebilir/gizleyebilir; seçim kalıcı.
- [ ] `npm test` + `typecheck` temiz; gerçek tarayıcıda klavye ve sürükleme testi.

## P2 · "PLANLA" → TARİHLİ PLAN KAYDI + HEMEN ONAYA

> **28.10.2026 — ✅ tamamlandı (T64/P2):** `src/core/plan-records.ts` +
> `plans.json` + `POST/GET /api/plans`; Dashboard "Planla" düğmesi planı açar ve
> tarihli kayıt bırakır (`d61cdad` öncesi `02d8ffc`, `674c4a7`).

### Neden
"Güvenli Kazanımlar" tablosu bugün **çıkmaz yol** (UX-005): ne bir düğme var,
ne bir kayıt. Kullanıcının isteği: tablodaki bir kazanç **planlanabilsin**,
plan **"Planlar"a aktarılsın**, **tarihli bir kayıt** tutulsun ve **hemen onaya**
gidilsin. Kullanıcının cevabı (21.10.2026): *"Tarihli kayıt + hemen onaya"*.

### Akış
```
Güvenli Kazanımlar tablosu
  └─ satırda "Planla" düğmesi
       └─ POST /api/plans  { clusterKeys: [...], name? }
            ├─ kayit açılır  → durum 'pending', createdAt = şimdi   (KALICI)
            ├─ onay planı üretilir (DeleteService.createPlan) → planId
            └─ kayıt planId ile eşleşir
                 └─ ekran "Planlar"a gider: kayıt + onay paneli (TASI)
                      └─ onay → kayıt 'executed', executedAt = şimdi
                           └─ "Geçmiş"te tarihli kayıt
```

### Motor + şema
```ts
export type PlanRecordStatus = 'pending' | 'executed' | 'cancelled' | 'failed';
export type PlanRecordSource = 'dashboard' | 'disk' | 'api';

export interface PlanRecordView {
  id: string; name: string;
  createdAt: number; executedAt?: number;
  status: PlanRecordStatus; source: PlanRecordSource;
  clusterKeys: string[]; clusterTitles: string[];
  clusterCount: number; targetCount: number; bytes: number;
  freedBytes?: number; removed?: number; error?: string;
}
```

- `src/core/plan-records.ts` **(yeni)** — `PlanRecord` + `PlanRecordState`
  (geçiş kuralları: yalnız `pending → executed|cancelled|failed`) + `PlanRecords`
  (sayım, sıralama — **yeni kayıt en üstte**, görünüm). Saf TS.
- `src/store/plan-records.ts` **(yeni)** — `%LOCALAPPDATA%\residue\plans.json`
  (atomik yazım; `src/store/schedules.ts` kalıbı).
- `src/services/plan-record-service.ts` **(yeni)** — list / create / markExecuted /
  cancel. `DeleteService` ve `ScanService` bağımlılıkları.
- `POST /api/execute` → plan `planId`'siyle eşleşen kayıt `executed` olur.

### Arayüz
- Tablonun her satırında **"Planla"** düğmesi (yalnız `safeWins` için).
- Planlama sonrası: **"Planlar" ekranı** açılır; en üstte yeni kayıt + onay
  paneli, altında kayıt listesi (tarihli), en altta geçmiş.
- **Onay dili değişmez:** `TASI` (kasaya taşıma). Kalıcı silme hâlâ yok.

### Kabul ölçütü
- [ ] Kayıt kalıcı; sunucu yeniden başlatılsa da listede.
- [ ] "Planla" → onay ekranı açılır, `TASI` yazılır, kasaya taşınır.
- [ ] Geçmişte tarih + sonuç (kazanılan bayt, kaldırılan öge) görünür.
- [ ] Kayıt **hiçbir** otomatik silme tetiklemez; yalnız kullanıcı onayı.
- [ ] `ApprovalRules` yeni tür gerektirmez (`vaultMove` = `TASI` yeter).

## P3 · "PLANLAR" BİLGİ MİMARİSİ + MENÜ ROZETİ

> **28.10.2026 — ✅ tamamlandı (T64/P3):** menüde `Plan (n)` rozeti; sayım
> motorda (`src/core/plan-badge.ts`), `aria-label` "Planlar: {total} kayıt,
> {pending} bekleyen" (`6a41dd6`).

### Neden
Sol menüde iki benzer madde var: **"Plan"** (Disk'te seçim yapınca açılan tek
seferlik onay ekranı) ve **"Planlar"** (zamanlama + geçmiş). Kullanıcı:
*"plan ismi planlar olmalı, çünkü planlama disk içinde yapılmıyor mu"* —
yani planlama **Disk'te** olur; menüdeki madde bir *planlama yeri* değil,
**planların listesi** olmalı. Ayrıca: *"eğer plan var ise soldaki Plan
menüsüne kaç plan var ise badge verilmeli"*.

### Karar (açık soru kaldı — 21.10.2026'da kullanıcı seçmedi)
| Seçenek | Sonuç |
|---|---|
| **A — Tek "Planlar"** *(önerilen)* | "Plan" ve "Planlar" tek maddede birleşir: **Onay bekleyen** + **Planlanmış işler** + **Geçmiş**. Rozet = toplam. |
| **B — Yeniden adlandır** | "Plan" → **"Planlar"**, mevcut "Planlar" → **"Zamanlama"**. Rozet "Planlar"da. |
| **C — Olduğu gibi** | İki madde kalır; rozet yalnız mevcut "Planlar"da. |

> Not: Seçenek A, "Planlar"ın **planların listesi** olma fikrini en temiz
> karşılar. Seçenek B daha az risklidir. **Kullanıcı seçimi bekleniyor.**
>
> **22.10.2026 uygulaması:** mevcut "Planlar" → **"Zamanlanmış"** olarak
> yeniden adlandırıldı (Seçenek B'nin bir parçası); "Plan" tek seferlik onay
> ekranı olarak kaldı. Menü rozeti hâlâ açık.

### Rozet
- Rozet **sayıdır**, motor sayar (`DashboardResponse` → `plans.total`,
  `plans.pending`, `schedules.rules`). Arayüz yalnız basar.
- 0 ise rozet gösterilmez.
- `aria-label`: "Planlar: 3 kayıt, 1 bekleyen" (TR/EN).

## P5 · "ARAÇLARDA 0 B" → "BİLİNMIYOR" (UX-002)

### Neden
API `cli` defterinde **4.025.009.588 bayt** döndürüyor; ekran **"Araçlarda
0 B"** diyor. Sebep: `DashboardService` envanteri **tetiklemiyor**
(`this.inventory.getLast()`); envanter yoksa `cliBytes = 0`.
Kullanıcı "kurulu CLI aracım yok" diye okuyor — gerçekte 3.7 GB var.

### Yapılacak
- Motor, envanter yoksa defteri `null` (bilinmiyor) olarak işaretler; `0`
  ile `bilinmiyor` **ayrı** gösterilir ("Araçlarda: bilinmiyor — envanter
  çalıştırılmalı" + "Araçlar"a giden düğme).
- `DashboardLedgerView.bytes` → `number | null`.
- Envanter **tetiklenmez** (ağır iş; mevcut kural korunur) — yalnızca
  **anlaşılmaz** olmaktan çıkar.
